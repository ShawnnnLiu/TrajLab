TrajectoryDB

Which components exist, which we build, and how they fit together.

Architecture

The brief names two building blocks: TrajectoryDB for the run record, StateFork for branchable environment state. TrajectoryDB is a vision paper, so Harbor and ATIF stand in for it. StateFork is a working system we plug in. The link between them is the part we implement.

  • Research goal
    Answer analysis questions about agent runs faster, or with much less analyst effort, than ad hoc workflows, without losing accuracy or provenance. Project #16.
    • TrajectoryDB concept
      One store holding every run: its trajectory plus a checkpoint after each step, linked.
      • Harbor existing
        The runner. Runs the agent on a task, grades it, writes the trajectory.
        • Docker existing
          The sandbox each task runs in.
      • ATIF existing
        The file format a trajectory is written in. Has a slot for "checkpoint taken here".
    • The link we build
      Checkpoint after every tool call, keyed by the call's id, written back into the trajectory.
    • StateFork existing
      DAPLab's environment versioning: checkpoint, restore, and fork a running sandbox.
      • docker commit existing
        First backend. Filesystem only. Used until the pipeline works end to end.
      • StateFork attach later
        Second backend, same interface. Build step 8.

Components

TrajectoryDBconcept

A store of agent runs where every step has two halves: the action, from the trajectory, and the resulting environment state, from a checkpoint. Both halves carry the same step id, so it can serve the five question classes in the brief, which neither half answers alone:

  • Recurring strategies and action sequences
  • Where successful and failed runs diverge
  • Whether the agent follows an expected process
  • Which actions cause consequential environment changes
  • How early success, failure, or a safety violation is detectable

No existing system provides this. Harbor and ATIF cover the action half, StateFork the state half. We build the join.

Harborexisting

The runner. Given a Terminal-Bench task and an agent (Claude Code), it builds a Docker sandbox, runs the agent inside, grades the result, and writes one directory per run with the trajectory, the score, and the cost.

It does
  • Run many tasks in parallel, safely isolated
  • Grade each run (pass / fail, tokens, dollars)
  • Write the trajectory in ATIF
  • Pass Claude Code settings through, which is how our hook gets in
It does not
  • Record the environment state at any point
  • Give us a signal while the agent is running
  • Remember where the agent's memory got summarized mid-run

Harbor stays a pinned, unmodified dependency. Everything we add attaches from outside.

ATIFexisting

Agent Trajectory Interchange Format. A JSON file, one entry per step: source (agent, user, or system), message, tool calls, and tool results. Harbor writes it and ships a validator. Two properties matter for us: every tool call carries an id, and the format reserves system steps for events such as checkpoint creation.

An agent step as Harbor writes it, followed by the checkpoint step we insert:

{ "step_id": 12, "source": "agent",
  "tool_calls": [{ "tool_call_id": "toolu_01A…",
                   "function_name": "Bash",
                   "arguments": { "command": "make test" } }] }

{ "step_id": 13, "source": "system",            ← ours
  "message": "checkpoint after toolu_01A…",
  "observation": { "checkpoint_id": "sha256:…", "backend": "docker_commit" } }
StateForkexisting

DAPLab's environment branching interface (arXiv:2510.05556; corrected 2026-09-23, there is no SOSP paper). StateFork is the common snapshot/restore/fork interface and benchmark; the CRIU checkpointing lives in its Waypoint backend (CRIU + OverlayFS, Linux-only, root), while its Docker attach mode snapshots with docker commit. This is the state half of TrajectoryDB and it exists today; we plug it in rather than build it. Dean covers the mechanism.

Order of operations: the first backend is docker commit, which captures the filesystem and loses shell state and memory, enough for file-level questions and for proving the pipeline. StateFork attaches behind the same backend interface afterwards, so the swap is a config change, not a rewrite; note (corrected 2026-09-23) its Docker attach mode is also docker commit underneath, so shell state and memory are only captured once we run its Waypoint/CRIU backends on a root Linux host. Its virtual snapshots stay off: Terminal-Bench runs are not deterministic, so every checkpoint is physical (ADR-0002).

The linkwe build

Not provided by any component above. After every tool call that can change the sandbox, take a checkpoint tagged with that call's id. The same id is in the trajectory, so each step maps to exactly one checkpoint. Three parts:

  • Hook, inside the sandbox: Claude Code runs it after each tool call. It writes a request and waits for an ack.
  • Watcher, on the host: sees the request, takes the checkpoint, writes the ack.
  • Post-processing, after the run: inserts one checkpoint step per tool call into the trajectory, and restores the context compaction boundaries that Harbor's converter drops.

The baseline

Why not hand the whole trace to a long-context model and ask what went wrong? TRAIL measured that. A 2026 follow-up says a newer model does not fix it, and says why.

TRAILprior work

A newer model did not help localization
  • GPT-5.4 on the whole trace beats the 2025 model on category F1, both splits, but trails it on span localization and joint accuracy, both splits.
  • That is with GPT-5.4's longest 6% / 23% of traces dropped. TRAIL shows accuracy falls with length, so the exclusion favors GPT-5.4.
A new representation did
  • Same model, same benchmark, same scoring code: GAIA joint 0.146 → 0.616, SWE localization 0.070 → 0.860.
  • Their conclusion, quoted: “evaluation methodology, not model capability, is the bottleneck.”

Read across rows with care. The two whole-trace rows are two labs' runs a year apart: Deepchecks does not say whether it reused TRAIL's prompt, how many runs it averaged, or GPT-5.4's reasoning effort, and neither paper reports traces scored per row. Within Deepchecks, the whole-trace row covers 94% / 77% of traces and the span row 100% (dropped vs. zeroed: not stated); the span row uses different prompts, adds agent-level metrics, and passes through an LLM mapper into TRAIL's categories, while baselines emit TRAIL labels directly. Loc. and joint are precision over predicted spans; neither paper reports recall.
